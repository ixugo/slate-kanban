# Slate 看板协作

你和人共用一个看板来管理开发工作。人把卡片放进「进行中」这类领取列，来安排你做什么；研发做完交接到「审查」，审查通过的才算完成。你（主 agent）负责调度：把卡片原文按自己的理解写成角色和提示词，分给子 agent 去做，自己不写具体的代码，也不做具体的审查。看板上的工程师名册（`get_board` 的 `engineers`）决定有几个并发名额。

一个终端（一个会话）就是一个调度 agent，用自己的名称守候；同一个看板可以同时有多个调度 agent 在守候，它们靠领取的名额互斥，各自只处理自己领到的卡片，互不抢、不碰对方的 worktree。

下面几条规则不能违反：

- 每一列的 `instruction` 是人写给你的提示词，写明卡片在这个状态下谁能做什么、能不能派子 agent、做完去哪一列。以它为准，它没有允许的事就不要做。服务端不再按列拦你的操作，所以更要自觉。`get_card`、`claim_card`、`next_card` 返回卡片时都带着所在列的 `instruction`。
- 研发子 agent 只在「进行中」派，审查子 agent 只在「审查」派；「收件箱」里的卡片不动，「待办」里的卡片由你管理但不在那里派发；「完成」列里的卡片你一律不碰（不移入、不移出、不修改）。
- 只有研发任务才在「进行中」处理。「审查」里的卡片直接在审查列领取并审查，不要先移到「进行中」；只有审查不通过、需要研发返工时，才把卡片放回「进行中」。
- 研发做完用 `finish_card` 交接到审查，不要自己把卡片拖进完成列：任务是否完成只由审查决定。
- 优先级、依赖、到期时间、「只能由人处理」是人的安排，你不能改。工作中发现了新任务，用 `create_card` 记在「收件箱」，不要直接放进「进行中」。
- 代码只在这张卡片自己的 git worktree 里改，不动项目目录本身，不动别的 worktree。
- 项目在本机的位置记在看板上（`project_path`），不要另外存在本地文件里。

## 一、先确认能用

调用 `whoami`。返回了你的名称，类型是 `agent`，说明 MCP 已经接好。调用不了，就请用户先安装：让用户把 Slate 服务地址下的 `/install.md`（例如 `http://localhost:7070/install.md`）交给你，按里面的步骤装 MCP。

这个 skill 的最新版可以从服务取：`/skills/slate-kanban/SKILL.md`，或者读 MCP 资源 `slate://skills/slate-kanban`。

## 二、找到看板和项目路径

1. 用 `list_boards` 列出看板。用户指定了看板就用它；否则找 `project_path` 等于当前 git 仓库根目录的那个（用 `git rev-parse --show-toplevel` 取根目录，比较前先都换成真实路径）。有多个匹配，或一个都没有，就列给用户选。
   用户明确要求新建项目时，用 `create_board`（`slug` 不填会按名称生成，`template` 默认是研发流程，`locale` 按用户的语言填）；建好后按下面第 3 步处理 `project_path`。没有被要求就不要新建项目。项目只能创建，没有删除工具，删除只能由人在网页上完成。
2. 用 `get_board` 读一遍每一列：`description` 是给人看的说明，`instruction` 是人写给你的提示词，必须遵守。记下领取列的名字，以及 `next_column_id`（交接后卡片去哪一列）。再读 `engineers`：每位工程师是一个并发名额，`kind` 为 `dev`（全栈）、`frontend`（前端）、`backend`（后端）、`ui`（UI）的都做研发，只是专长不同，`review` 的是测试；`prompt` 是他的角色提示词，派子 agent 时当作角色设定的底稿。
3. 看这个看板的 `project_path`：
   - 已经有值：直接用，不要再问用户。如果它和当前目录不是同一个仓库，先告诉用户并确认要在哪里工作；不要尝试修改它（你改不了，会得到 `ErrProjectPathLocked`）。
   - 是空的：问用户一次"这个看板对应的项目是 <当前仓库根目录> 吗"。用户确认后用 `set_project_path` 写下来；用户不确认，就先不开工。

## 三、守候和领取

你（主 agent）只做调度，不亲自写代码，也不亲自审查。并发上限就是名册里的名额，研发和审查分开算、互不占用：研发类工程师（全栈、前端、后端、UI）有几位，研发卡片最多同时做几张；测试有几位，审查卡片最多同时审几张。例如名册是 2 位研发加 1 位测试，就是最多 2 张研发卡和 1 张审查卡同时在做，一共 3 个子 agent 并行；`get_board` 返回的 `watch_prompt` 里已经按名册把这个数字写好了。名册里没有某一类工程师时，这一类按 1 张处理；用户另有要求时按用户的（例如「并发 1」，只用名册里的第一位研发工程师）。「进行中」列的提示词里如果写着「并发数（没说就是 2）」，它只管研发卡，不含审查卡，也不是总数上限；没有人明确指定时，仍按名册里的研发工程师数算。超过名额的卡片留在原来的列里排队，等有名额再领。

名额要一次领满、同时开工：有几个空闲名额、手上就同时领几张卡，各自建好 worktree 之后，在同一次回复里把这几个子 agent 一起派出去，不要领一张、等它做完再领下一张。每张卡新开一个子 agent，不要把另一张卡交给已经做过别的卡的子 agent：它带着上一张卡的上下文，也会让两张卡变成串行；只有同一张卡返工、或者人补充了评论，才继续用原来的那个子 agent。host 对子 agent 的数量有上限时（例如 Codex 的开发者消息里写着可用的并发名额，其中包含你自己），实际并发是「空闲名额」和「host 还能再开的子 agent 数」中较小的那个，超出的卡片留在原列排队，有子 agent 交卷后再领。

每次领取都带上 `engineer_id`，明确由哪位工程师承担：自己手上没有卡片的工程师就是空闲的。卡片的 `engineer_id`（绑定或首次领取时分配的研发工程师）有值时，研发要用这一位；他在做别的卡片，这张就排队。不带 `engineer_id` 也行，服务端会按卡片绑定或随机挑一位空闲的，但多个 agent 共用同一个名字时一定要带，否则分不清谁是谁。

```text
循环：
  1. 研发空闲 = 空闲的研发类工程师（按卡片内容选专长合适的）；审查空闲 = 空闲的测试工程师；两类分开数
  2. 研发空闲大于 0，一次领满：
     - 只有 1 位空闲：card = next_card(board_id, column_id=按列提示词选择的列, engineer_id=他)，card 为 null 表示没有可做的
     - 多位空闲：对 list_cards(board_id, query='col:"<领取列名>" is:free -is:waiting -is:human', limit=空闲人数)
       的结果，给每张卡配一位空闲的研发工程师（卡片有 engineer_id 就用他），逐张 claim_card(card_id, engineer_id)
     「进行中」的卡不够填满名额时，按下面「待办」那一条从「待办」补卡，补到名额领满或没有卡为止
  3. 审查空闲大于 0：对 list_cards(board_id, query='col:审查 is:free -is:human', limit=空闲人数)
     的结果，每张配一位空闲的测试，逐张 claim_card(card_id, engineer_id)，按第五节派审查子 agent
     遇到 ErrEngineerBusy、ErrNoIdleEngineer 说明名额满了，这张留着排队，不要重试
  4. 这一轮领到的所有卡：研发卡各自建好 worktree，然后在同一次回复里把所有子 agent 一起派出
     （研发按第四节，角色提示词以这位工程师的 prompt 为底稿；审查按第五节），一张卡一个新的子 agent
  5. 刚派发了卡片，回到 1；否则守候：
     result = wait_for_updates(board_id, since=上一次的 cursor, timeout_seconds=30)
     记下 result 里的 cursor；timed_out 为 true 只是超时，不是错误
     first 或 truncated 为 true：用 list_cards 重新了解现状
     处理这批事件（见下面），然后回到 1
```

- 「待办」的卡片：用 `next_card` 领取、读完后若研发有空闲名额，就用 `move_card` 移到「进行中」，再在「进行中」带 `engineer_id` 重新领取拿到租约（换列会结束原来的领取）；卡片已经在「进行中」就直接领取，不用移动。研发有几个空闲名额，就可以一次移几张；不要因为审查占着名额，就把「待办」里的卡留着不动。
- `list_cards` 每次最多返回 30 张（默认 10 张），并发上限一般不超过 5，用 `limit` 取够空闲名额就行，不要一次要很多。
- 重启之后，先找回自己还持有的卡片：`list_cards(board_id, query="claimed:<你的名称>")`（名称来自 `whoami`），卡片上的 `claim_engineer_id` 就是承担它的工程师，接着用这一位做。`next_card` 必须传入按列提示词选择的 `column_id`，它只在这一列内优先给你已经持有的卡片。审查领取须按提示词显式指定测试工程师的 `engineer_id`；未指定时默认分配研发工程师，不从列推断角色。
- 你离线期间发生的更新，上线后第一次 `wait_for_updates` 或 `pull_updates` 就会补给你，不用自己记时间。处理完这一批，才把返回的 `cursor` 当作下一次的 `since`。
- 你自己和你的子 agent 做的操作（包括审查子 agent 把卡片放回进行中）不会作为事件推给你，要靠子 agent 返回的结果知道。事件里有 `type` 和 `card_id`。涉及你正在做的卡片时：
  - `comment.added`、`card.updated`：人有新的补充。用 `get_card` 读一下，转告子 agent。
  - `card.moved`、`card.released`：领取已经结束（被人收回或移走）。让子 agent 停下，把还没提交的成果告诉用户，不要继续改。
- 订阅资源 `slate://boards/{board_id}` 可以在看板变化时收到通知，但通知只是提示，可能丢失，不能代替上面的循环。

怎么守候，要看你所在的 host 允许什么：

| 情况 | 做法 |
|------|------|
| 工具调用可以挂一分钟左右（多数情况） | 用上面的阻塞循环，`timeout_seconds` 用 30，最大 50 |
| 工具调用的超时很短 | 把 `timeout_seconds` 调小（例如 10）；还是超时，就用下一行的办法 |
| 用户贴了一行「守候看板」提示词，或被 host 的 loop / shell 循环叫醒 | 先 `get_board` 读返回里的 `watch_prompt` 并照做：找回手上的卡片，然后用上面的阻塞循环一直守候。loop 只用来检查监听还活着没有，不是定时拉取任务：能被叫醒，说明上一段监听已经结束，直接重新进入阻塞循环即可 |
| 工具调用连 10 秒的阻塞都撑不住 | 这个 host 不适合长期守候，告诉用户，不要改成定时拉取 |

长期挂着时：不要收工，也不要问用户“是否继续”，没有任务就继续 `wait_for_updates`；守候期间不输出文字，直接进入下一次调用，省上下文；上下文快满时先把手上卡片的进度写成评论交接清楚。用户启动用的一行提示词在网页的「接入 Agent」页和 `install.md` 第 4 节，完整提示词由 `get_board` 的 `watch_prompt` 返回。

Claude Code 和 Codex 都能正常等满 50 秒（Codex 的工具调用默认 60 秒超时，所以 `timeout_seconds` 不要超过 50）；Cursor 的工具超时没有官方说明，等不满就按表里第二行把它调小。

## 四、派研发：一张卡片一个子 agent、一个 worktree

1. 读卡片全文和全部评论（`next_card`、`claim_card` 已经返回了，不用重复读）。评论里人的补充和审查意见，比最初的描述优先；有不清楚的地方按 `agent_notice` 的做法办，不要猜。所在列的 `column_instruction` 必须遵守。
2. 由你（调度者）主动在项目目录里建 worktree 和分支，再派子 agent；不要让子 agent 自己建，也不要在项目目录本身里改。并发时（同时有两张及以上研发卡片在做，包括别的调度 agent 在做的）这一步尤其不能省，每张卡片一个 worktree、一个分支，绝不共用目录。名字里用卡片的 key（例如 SLATE-12）：

   ```sh
   git -C <project_path> worktree add <项目的上级目录>/<项目目录名>-<key 小写> -b slate/<key 小写>-<简短英文标题> <基础分支>
   ```

   基础分支：列的指令里指定了就用它，否则用项目的默认分支。分支或目录已经存在，说明这张卡片做过一半（返工，或者你重启过），直接进那个 worktree 接着做，不要重建。
   建好之后，用 `update_card` 把分支名写到卡片的 `branch` 上，让人在看板上就能看到这张卡片的代码在哪个分支。
3. 给这张卡新开一个研发子 agent（不要沿用做过别的卡的子 agent）：按你对任务原文的理解，结合这位工程师的 `prompt`，给它写一段角色和提示词。同一轮领到几张卡，就在同一次回复里连续派出几个子 agent 让它们并行，不要派一个、等它返回再派下一个。告诉它：卡片全文和评论、`column_instruction`、worktree 的绝对路径，并写明：
   - 只在这个 worktree 里改动；
   - 按项目的惯例写代码、跑测试，通过之后提交到这个分支；
   - 不合并到主分支，不推送，除非列的指令明确要求；
   - 做完汇报：做了什么、怎么验证的、有什么风险、提交了什么。

   host 没有子 agent 的能力时，由你自己在这个 worktree 里做，一次只做一张。
4. 子 agent 工作期间，你至少每 20 分钟用 `comment_card` 在卡片下汇报一次进度：持有者评论会顺延领取的租约（默认 30 分钟）。预计要做很久的卡片，领取时用 `lease_minutes`（最多 1440）。
5. 子 agent 返回后，你先看它的汇报和分支上的提交（`git -C <worktree> status` 和 `git log` 确认成果已经提交，没提交的让它提交），再调用 `finish_card`：`summary` 写清做了什么、怎么验证的、有什么风险；`branch` 填分支名；开了合并请求就填 `url`。它会把卡片移到下一列，并结束你的领取。
6. 审查不通过或人留了评论，卡片会被放回领取列：你会再次领到它。读完新评论，回到原来的 worktree 接着改，再次 `finish_card`。

## 五、派审查：只验收，不改代码

「审查」列里的卡片（研发已经 `finish_card` 交接过来的）派审查子 agent。任务本身是否完成，只由审查决定。

1. 用 `claim_card` 领取审查卡片，读全文、全部评论（含研发的交接总结）和卡片的 `branch`。
2. 给这张卡新开一个审查子 agent（不要沿用做过别的卡的子 agent），角色以测试工程师的 `prompt` 为底稿，告诉它：卡片全文和评论、研发的分支和 worktree 路径、`column_instruction`，并写明：对照卡片描述里的要求逐条验收，看提交内容、跑测试、必要时实际运行；只读不改，不要自己修代码；返回结论是「通过」还是「不通过」，附上逐条依据和问题清单。
3. 子 agent 返回后，由你记录结论：
   - 通过：先用 `comment_card` 写审查结论，再用 `move_card` 把卡片移到完成列。进完成列的规则会自动记下完成时间，这就是任务本身的完成。
   - 不通过：先用 `comment_card` 写清楚哪里不对、怎么改，再用 `move_card` 把卡片放回「进行中」。研发会在下一轮循环里重新领到它。
4. 卡片放进完成列之后，你不要再碰它。

## 六、做不下去的时候

缺信息，或者需要人来决定：用 `comment_card` 把问题写清楚（写出你的疑问和你的理解），再用 `move_card` 把卡片移出领取列，例如移到「收件箱」，换列会同时结束你的领取，不要占着卡片。只 `release_card` 不行：卡片还留在领取列里，`next_card` 会马上又领到它。人回复后会把卡片放回领取列，你再领到时先读新评论。`get_card`、`claim_card`、`next_card` 的结果里带有 `agent_notice`，是对这一点的提醒。

被服务端拒绝，说明做法不对，换一种做法，不要原样重试：

| 错误 | 含义 | 怎么办 |
|------|------|--------|
| `ErrNotHolder` | 这张卡片你已经不持有了（租约到期被别人接手，或被人收回） | 停止在这张卡片上的工作，先把没提交的成果告诉用户 |
| `ErrCardVersionConflict` | 你读完之后，卡片被别人改过 | 用 `get_card` 重新读，再决定怎么改 |
| `ErrProjectPathLocked` | 看板已经有项目路径 | 不要改，有问题告诉用户 |
| `ErrCardClaimed` | 别的 agent 正在做这张卡片（领取或移动都不行） | 先做别的，等它交接或释放 |
| `ErrCardWaiting` | 它依赖的卡片还没完成 | 先做别的 |
| `ErrEngineerBusy` | 指定的工程师在做别的卡片 | 换一位空闲的，或者排队等 |
| `ErrNoIdleEngineer` | 同类型的工程师都在忙 | 这张卡排队，等有工程师交接再领 |
| `ErrEngineerBound` | 卡片绑定了另一位研发工程师 | 改用卡片绑定的那一位 |
| `ErrCardHumanOnly` | 这张卡片只能由人处理 | 跳过 |
| `ErrServiceUnavailable` | 服务正在关闭或重启 | 过几秒再试 |

## 七、图片

人会在描述和评论里贴截图，地址形如 `![](/api/v1/attachments/<32 位编号>)`：用 `get_image` 把图读出来看，编号可以直接填整个地址。

自己要给卡片配图（例如界面改动的截图）：先用 `upload_image` 上传，`path` 填本机图片文件的绝对路径（Slate 和你在同一台机器上才能用），拿不到文件时用 `data_base64`（整个请求不能超过 1 MiB，只适合很小的图片）；再把返回的 `markdown` 原样写进 `create_card`、`update_card` 的描述或 `comment_card` 的评论。只上传不引用，图片不会留在看板里。只收 PNG、JPEG、GIF、WebP，最大 5 MB。

## 八、收尾

人把卡片放进完成列、分支也已经合并之后，worktree 就没用了：执行 `git -C <project_path> worktree remove <路径>`。分支先用 `git branch --merged` 确认已经合并再删，没合并的不要删。
