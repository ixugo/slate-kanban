# Slate 看板协作

你和人共用一个看板来管理开发工作。人把任务放进「进行中」这类领取列，来安排你做什么；研发做完交接到「审查」，审查通过的才算完成。你（主 agent）负责调度：把任务原文按自己的理解写成角色和提示词，分给子 agent 去做，自己不写具体的代码，也不做具体的审查。看板上的工程师名册（`get_board` 的 `engineers`）决定有几个并发名额。

一个终端（一个会话）就是一个调度 agent，用自己的名称守候；同一个看板可以同时有多个调度 agent 在守候，它们靠领取的名额互斥，各自只处理自己领到的任务，互不抢、不碰对方的 worktree。

下面几条规则不能违反：

- 每一列的 `instruction` 是人写给你的提示词，写明任务在这个状态下谁能做什么、能不能派子 agent、做完去哪一列。以它为准，它没有允许的事就不要做。服务端不再按列拦你的操作，所以更要自觉。`get_card`、`claim_card`、`next_card` 返回任务时都带着所在列的 `instruction`。
- 默认五列中，「待办」是必须主动检查的调度入口，研发子 agent 只在「进行中」派，审查子 agent 只在「审查」派。「收件箱」和「完成」平时跳过。自定义流程按列的 `instruction` 和 `next_column_id` 选择实际入口及去向。
- 只有研发任务才在「进行中」处理。「审查」里的任务直接在审查列领取并审查，不要先移到「进行中」；只有审查不通过、需要研发返工时，才把任务放回「进行中」。
- 研发做完用 `finish_card` 交接到审查，不要自己把任务拖进完成列：任务是否完成只由审查决定。
- 标签只能贴看板上已有的：领取任务后，对照任务内容用 `update_card` 的 `tag_ids` 调整标签，`tag_ids` 来自 `get_board` 的 `tags`；不要新建标签（不要用 `tags` 文字参数创建新标签），没有合适的就不贴。
- 实现了哪些内容必须写进描述：交接前用 `update_card` 在描述末尾补上「任务项」清单，已实现的写成 `- [x] 内容`，没做完的写成 `- [ ] 内容`。
- 优先级、依赖、到期时间、「只能由人处理」是人的安排，你不能改。工作中发现了新任务，用 `create_card` 记在「收件箱」，不要直接放进「进行中」。
- 代码只在这个任务自己的 git worktree 里改，不动项目目录本身，不动别的 worktree。
- 项目在本机的位置记在看板上（`project_path`），不要另外存在本地文件里。

## 一、先确认能用

调用 `whoami`。返回了你的名称，类型是 `agent`，说明 MCP 已经接好。MCP 尚未接通时，只报告连接状态和 Slate 服务的 `/install.md` 接入入口，不启动终端问答。

这个 skill 的最新版可以从服务取：`/skills/slate-kanban/SKILL.md`，或者读 MCP 资源 `slate://skills/slate-kanban`。

只有用户明确要求管理看板设置、列或自动化时，才调用 `enable_management` 在当前 MCP 会话显示管理工具。客户端未刷新列表时，传 `{"include_tools":true}` 获取管理工具目录，再在同一会话调用 `enable_management`，传入目标工具名 `tool` 和参数对象 `arguments`。只在实际执行用户要求的管理操作时传入这些参数。创建任务、领取、交接等日常工作直接用工作工具。

## 二、找到看板和项目路径

1. 用 `list_boards` 列出看板。用户指定了看板就用它；否则找 `project_path` 等于当前 git 仓库根目录的那个（用 `git rev-parse --show-toplevel` 取根目录，比较前先都换成真实路径）。没有唯一匹配且用户未指定看板时，只报告现状，等待明确的看板选择。不要猜选看板或在终端触发阻塞式提问。
   用户明确要求新建项目时，用 `create_board`（`slug` 不填会按名称生成，`template` 默认是研发流程，`locale` 按用户的语言填）；建好后按下面第 3 步处理 `project_path`。没有被要求就不要新建项目。项目只能创建，没有删除工具，删除只能由人在网页上完成。
2. 用 `get_board` 读一遍每一列：`description` 是给人看的说明，`instruction` 是人写给你的提示词，必须遵守。记下领取列的名字，以及 `next_column_id`（交接后任务去哪一列）。再读 `engineers`：每位工程师是一个并发名额，`kind` 为 `dev`（全栈）、`frontend`（前端）、`backend`（后端）、`ui`（UI）的都做研发，只是专长不同，`review` 的是测试；`prompt` 是他的角色提示词，派子 agent 时当作角色设定的底稿。
3. 核对看板的 `project_path` 与当前仓库。若缺失或不匹配，暂停依赖该路径的工作，在这个看板的收件箱复用或创建一项配置任务，记录待确认的绝对路径或不一致之处。没有可写的看板入口时只报告状态。
   - 路径为空且有人在看板上明确确认后，用 `set_project_path` 登记。已有值只能由人调整；如果会话启动在错误目录，也可由人从正确仓库重启。
   - 守候期间留意这项配置任务的回复和 `board.updated`。收到相关事件，或监听返回 `first`、`truncated` 时，复查配置任务和 `get_board` 的路径。确认匹配后恢复受影响的工作，其他可办事项照常处理。

只需定位项目时可传 `list_boards({"summary":true})`，日常读取列规则和名册可传 `get_board({"board_id":1,"include_watch_prompt":false})`。启动或恢复守候时保留完整守候说明。

列表查询：`list_cards` 的 query 用空格分隔条件，所有条件都必须满足；词前减号取反，双引号内可含空格。可用关键词、`tag:`、`col:`（列名或编号）、`key:`、`title:`、`desc:`、`priority:`（等级、数字或比较）、`claimed:`、`is:`、`has:`、`no:`、`due:`、`created:` 和 `updated:`。常用条件是 `is:free`、`is:waiting`、`is:human` 和 `is:done`，日期可用 `due:today` 或 `due:<2026-12-01`。标签、列、编号、优先级、持有者以及 is/has/no 的值可用竖线多选，如 `tag:bug|ui`。

## 三、守候和领取

你（主 agent）只做调度，不亲自写代码，也不亲自审查。并发上限就是名册里的名额，研发和审查分开算、互不占用：研发类工程师（全栈、前端、后端、UI）有几位，研发任务最多同时做几个；测试有几位，审查任务最多同时审几个。例如名册是 2 位研发加 1 位测试，就是最多 2 个研发任务和 1 个审查任务同时在做，一共 3 个子 agent 并行；`get_board` 返回的 `watch_prompt` 里已经按名册把这个数字写好了。名册里没有某一类工程师时，这一类按 1 个处理；用户另有要求时按用户的（例如「并发 1」，只用名册里的第一位研发工程师）。「进行中」列的提示词里如果写着「并发数（没说就是 2）」，它只管研发任务，不含审查任务，也不是总数上限；没有人明确指定时，仍按名册里的研发工程师数算。超过名额的任务留在原来的列里排队，等有名额再领。

名额要一次领满、同时开工：有几个空闲名额、手上就同时领几个任务，各自建好 worktree 之后，在同一次回复里把这几个子 agent 一起派出去，不要领一个、等它做完再领下一个。每个任务新开一个子 agent，不要把另一个任务交给已经做过别的任务的子 agent：它带着上一个任务的上下文，也会让两个任务变成串行；只有同一个任务返工、或者人补充了评论，才继续用原来的那个子 agent。host 对子 agent 的数量有上限时（例如 Codex 的开发者消息里写着可用的并发名额，其中包含你自己），实际并发是「空闲名额」和「host 还能再开的子 agent 数」中较小的那个，超出的任务留在原列排队，有子 agent 交卷后再领。

每次领取都带上 `engineer_id`，明确由哪位工程师承担：自己手上没有任务的工程师就是空闲的。任务的 `engineer_id`（绑定或首次领取时分配的研发工程师）有值时，研发要用这一位；他在做别的任务，这个任务就排队。不带 `engineer_id` 也行，服务端会按任务绑定或随机挑一位空闲的，但多个 agent 共用同一个名字时一定要带，否则分不清谁是谁。

```text
循环：
  1. 研发空闲 = 空闲的研发类工程师（按任务内容选专长合适的）；审查空闲 = 空闲的测试工程师；两类分开数
  2. 研发空闲大于 0，一次领满：
     - 只有 1 位空闲：card = next_card(board_id, column_id=按列提示词选择的研发执行列, engineer_id=他)，card 为 null 表示当前列没有可领的
     - 多位空闲：对 list_cards(board_id, query='col:"<领取列名>" is:free -is:waiting -is:human', limit=空闲人数)
       的结果，给每个任务配一位空闲的研发工程师（任务有 engineer_id 就用他），逐个 claim_card(card_id, engineer_id)
     研发还有空位就必须主动检查「待办」，包括「进行中」为空时。按下面的「待办」流程补到满员或没有可领任务为止
  3. 审查空闲大于 0：对 list_cards(board_id, query='col:"<实际审查列名>" is:free -is:human', limit=空闲人数)
     的结果，每个配一位空闲的测试，逐个 claim_card(card_id, engineer_id)，按第五节派审查子 agent
     遇到 ErrEngineerBusy、ErrNoIdleEngineer 说明名额满了，这个任务留着排队，不要重试
  4. 这一轮领到的所有任务：研发任务各自建好 worktree，然后在同一次回复里把所有子 agent 一起派出
     （研发按第四节，角色提示词以这位工程师的 prompt 为底稿；审查按第五节），一个任务一个新的子 agent
  5. 刚派发了任务，回到 1；否则守候：
     result = wait_for_updates(board_id, since=上一次的 cursor, timeout_seconds=按下表选择)
     记下 result 里的 cursor；timed_out 为 true 只是超时，不是错误
     first 或 truncated 为 true：用 list_cards 重新了解现状
     处理这批事件（见下面），然后回到 1
```

- 「待办」的任务：有空闲研发名额时用 `next_card` 领取并读完描述、评论和依赖。清楚的任务用 `move_card` 移到「进行中」，带 `engineer_id` 重新领取后再派发（换列会结束原来的领取）。不清楚的任务先评论再移到「收件箱」。研发名额满员时留在「待办」排队。
- `list_cards` 每次最多返回 30 个（默认 10 个），并发上限一般不超过 5，用 `limit` 取够空闲名额就行，不要一次要很多。
- 重启之后，先找回自己还持有的任务：`list_cards(board_id, query="claimed:<你的名称>")`（名称来自 `whoami`），任务上的 `claim_engineer_id` 就是承担它的工程师，接着用这一位做。`next_card` 必须传入按列提示词选择的 `column_id`，它只在这一列内优先给你已经持有的任务。审查领取须按提示词显式指定测试工程师的 `engineer_id`；未指定时默认分配研发工程师，不从列推断角色。
- 你离线期间发生的更新，上线后第一次 `wait_for_updates` 或 `pull_updates` 就会补给你，不用自己记时间。处理完这一批，才把返回的 `cursor` 当作下一次的 `since`。
- 收到人的 `board.updated` 且 `payload.fields` 包含 `description`，或更新已截断（`truncated`）时，重新调用 `get_board`，以最新 `watch_prompt` 末尾的 AGENTS.md 项目说明为准。说明已清空时，停止应用旧内容。
- 你自己和你的子 agent 做的操作（包括审查子 agent 把任务放回进行中）不会作为事件推给你，要靠子 agent 返回的结果知道。事件里有 `type` 和 `card_id`。涉及你正在做的任务时：
  - `comment.added`、`card.updated`：人有新的补充。用 `get_card` 读一下，转告子 agent。
  - `card.released`：领取已经结束（被人收回，或租约到期后被别人接手，`payload.why` 为 `revoked`、`expired`）。让子 agent 停下，把还没提交的成果告诉用户，不要继续改。
  - `card.moved`：人把任务移了列。人移动不会收回领取，所以只有 `card.moved`、没有 `card.released` 时，任务仍然归你：用 `get_card` 看新位置和新评论，转告子 agent，继续做，按任务现在所在列的提示词判断后面怎么走。
- 订阅资源 `slate://boards/{board_id}` 可以在看板变化时收到通知，但通知只是提示，可能丢失，不能代替上面的循环。

怎么守候，要看你所在的 host 允许什么：

| 情况 | 做法 |
|------|------|
| 空闲且客户端和反向代理都已配置支持长等待 | 用 `timeout_seconds=3600`，服务端最多等 60 分钟。有变化立即返回 |
| 手上有任务、需要检查子 agent 或租约，或者客户端支持情况未知 | 用 `timeout_seconds=50` 或更短，确保到需要跟进时能及时回到调度循环 |
| 工具调用的超时很短 | 把 `timeout_seconds` 调小（例如 10）；还是超时，就用下一行的办法 |
| 用户贴了一行「守候看板」提示词，或被 host 的 loop / shell 循环叫醒 | 先 `get_board` 读返回里的 `watch_prompt` 并照做：找回手上的任务，然后用上面的阻塞循环一直守候。loop 只用来检查监听还活着没有，不是定时拉取任务：能被叫醒，说明上一段监听已经结束，直接重新进入阻塞循环即可 |
| 工具调用连 10 秒的阻塞都撑不住 | 这个 host 不适合长期守候，告诉用户，不要改成定时拉取 |

长期挂着时：不要收工，也不要问用户“是否继续”，没有任务就继续 `wait_for_updates`；守候期间不输出文字，直接进入下一次调用，省上下文；上下文快满时先把手上任务的进度写成评论交接清楚。用户启动用的一行提示词在网页的「接入 Agent」页和 `install.md` 第 4 节，完整提示词由 `get_board` 的 `watch_prompt` 返回。

Python 监听器触发的会话只做一轮。必要留言和交接已写入、领取已按流程处置且子 agent 已结束时，即可按派发提示返回本轮回执。卡片可以继续等待人工补验或等待依赖。派发结果未确认时，监听器保留待确认游标并暂停自动派发。用原启动参数加 `--status` 查看。确认上一轮已停止并核对卡片后，已处理用 `--resolve done`，确认可安全重跑用 `--resolve retry`，再用原命令启动。

macOS 图形登录会话可用原启动参数加 `--supervise enable`，让 LaunchAgent 每五分钟检查 Python 监听器。用 `--supervise status` 查看，用 `--supervise disable` 停用并保留游标。LaunchAgent 和交互会话的 `/loop 5m` 各自检查自己的监听入口。待确认派发须先通过 `--resolve done` 或 `--resolve retry` 人工处置，LaunchAgent 才会在下次检查恢复。

Codex 的工作视图配置用 `tool_timeout_sec = 3660`（秒）。Claude Code 的工作视图 HTTP 服务用 `timeout: 3660000`（毫秒），在专用守候会话中可用 `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS=0` 启动，确保客户端继续等待。具体安装和启动命令见 Slate 的 `/install.md`。链路上的代理也要允许超过 60 分钟的响应等待。超时或断线时先回到 50 秒或更短，按原游标续订；空超时直接续等。[Codex MCP 配置](https://developers.openai.com/codex/mcp) · [Claude Code 超时配置](https://code.claude.com/docs/en/env-vars#mcp_tool_timeout)

### 先把方案写到任务评论

研发和审查子 agent 接到任务后，先只读了解任务和相关代码，写一份简短方案发给调度者，然后暂停。研发方案说明准备改什么、怎么改和怎么验证；审查方案说明验收范围、检查步骤和测试。两种方案都要交代已知风险或疑问。若 host 只在子 agent 返回时才能取得结果，让它先返回方案，评论成功后再继续同一个子 agent 会话。

调度者确认自己仍持有任务后，用 `comment_card` 代发方案，注明是研发方案还是审查方案。评论成功后，通知子 agent 在原工作范围内继续；需要人决定的问题按第六节处理。host 没有子 agent 而由调度者直接做研发时，也要先用 `comment_card` 写下方案，再开始改动。

若评论请求超时等导致写入结果不明，先用 `get_card` 查同一调度者是否已发出该方案。只有确认未写入且仍持有任务才重试，同一错误最多重试两次。仍无法确认写入就暂停这个任务、报告卡点并继续处理其他任务。任务已被移动、收回或租约已失效时，停止这个任务的工作。

## 四、派研发：一个任务一个子 agent、一个 worktree

1. 读任务全文和全部评论（`next_card`、`claim_card` 已经返回了，不用重复读）。评论里人的补充和审查意见，比最初的描述优先；有不清楚的地方按 `agent_notice` 的做法办，不要猜。所在列的 `column_instruction` 必须遵守。
2. 由你（调度者）主动在项目目录里建 worktree 和分支，再派子 agent；不要让子 agent 自己建，也不要在项目目录本身里改。并发时（同时有两个及以上研发任务在做，包括别的调度 agent 在做的）这一步尤其不能省，每个任务一个 worktree、一个分支，绝不共用目录。名字里用任务的 key（例如 SLATE-12）：

   ```sh
   git -C <project_path> worktree add <项目的上级目录>/<项目目录名>-<key 小写> -b slate/<key 小写>-<简短英文标题> <基础分支>
   ```

   基础分支：列的指令里指定了就用它，否则用项目的默认分支。分支或目录已经存在，说明这个任务做过一半（返工，或者你重启过），直接进那个 worktree 接着做，不要重建。
   建好之后，用 `update_card` 把分支名写到任务的 `branch` 上，让人在看板上就能看到这个任务的代码在哪个分支。同时对照任务内容调整标签，只用看板上已有的标签，不新建。
3. 给这个任务新开一个研发子 agent（不要沿用做过别的任务的子 agent）：按你对任务原文的理解，结合这位工程师的 `prompt`，给它写一段角色和提示词。同一轮领到几个任务，就在同一次回复里连续派出几个子 agent 让它们并行，不要派一个、等它返回再派下一个。告诉它：任务全文和评论、`column_instruction`、worktree 的绝对路径，并写明：
   - 先只读拟定研发方案并回传给调度者，等调度者确认方案已写入评论再开工；
   - 只在这个 worktree 里改动；
   - 按项目的惯例写代码、跑测试，通过之后提交到这个分支；
   - 不合并到主分支，不推送，除非列的指令明确要求；
   - 做完汇报：做了什么、怎么验证的、有什么风险、提交了什么。

   host 没有子 agent 的能力时，由你自己在这个 worktree 里做，一次只做一个。
4. 子 agent 工作期间，你至少每 20 分钟用 `comment_card` 在任务下汇报一次进度：持有者评论会顺延领取的租约（默认 30 分钟）。预计要做很久的任务，领取时用 `lease_minutes`（最多 1440）。
5. 子 agent 返回后，你先看它的汇报和分支上的提交（`git -C <worktree> status` 和 `git log` 确认成果已经提交，没提交的让它提交），再用 `update_card` 在描述末尾补上或更新「任务项」清单（每项一行，已实现写 `- [x] 内容`，没做完写 `- [ ] 内容`；更新时保留原来的描述正文，不要整体覆盖丢内容），最后调用 `finish_card`：`summary` 写清做了什么、怎么验证的、有什么风险；`branch` 填分支名；开了合并请求就填 `url`。它会把任务移到下一列，并结束你的领取。
6. 审查不通过或人留了评论，任务会被放回领取列：你会再次领到它。读完新评论，回到原来的 worktree 接着改，同步更新描述里的任务项，再次 `finish_card`。

## 五、派审查：只验收，不改代码

「审查」列里的任务（研发已经 `finish_card` 交接过来的）派审查子 agent。任务本身是否完成，只由审查决定。

1. 用 `claim_card` 领取审查任务，读全文、全部评论（含研发的交接总结）和任务的 `branch`。
2. 给这个任务新开一个审查子 agent（不要沿用做过别的任务的子 agent），角色以测试工程师的 `prompt` 为底稿，告诉它任务全文和评论、研发的分支和 worktree 路径、`column_instruction`。先只读拟定方案并回传，等你确认方案已写入评论再开始验收。验收期间保持代码只读，对照原始要求逐条检查，回传验收结果和依据，注明实际执行的操作、命令及结果。页面验收要运行相关页面并回传实际效果截图及对应的检查项。发现问题时写明复现步骤和修正建议。
3. 用 `comment_card` 在任务下发布审查结论和证据。页面截图用 `upload_image` 上传，把返回的图片 Markdown 放在对应检查项旁。功能验收按审查清单逐项记录，已验证通过写 `- [x] 项目与证据`，未通过或未验证写 `- [ ] 项目与原因`。缺少必要证据时写明受限的检查项和原因，暂不判通过。
   - 通过：结论和证据评论成功后，适用本机专属 Slate 分支时按第八节合并、记录并清理。其他通过的任务用 `move_card` 移到完成列。进完成列的规则会自动记下完成时间，这就是任务本身的完成。
   - 确认不通过：结论、证据和修正建议评论成功后，用 `move_card` 把任务放回「进行中」。研发会在下一轮循环里重新领到它。
4. 任务放进完成列之后，只按第八节核对适用任务的本地合并结果和清理记录。

## 六、做不下去的时候

任务缺信息，或范围、验收与授权需要人决定时，始终通过看板澄清，禁止在终端触发阻塞式提问。用 `comment_card` 写清疑问和当前理解，评论成功后用 `move_card` 移回「收件箱」或列指令约定的澄清列。换列会结束领取，腾出的名额继续处理其他可办任务。只 `release_card` 会让这项任务马上被重新领到。人回复并将任务放回领取列后，重新领取时先读新评论。`get_card`、`claim_card`、`next_card` 的 `agent_notice` 会提醒这一步。

看板确认用于澄清任务，不替代宿主权限。缺少权限时暂停受影响的动作，在看板说明。MCP 鉴权失败、连续三次连不上或没有可写看板入口时，只报告状态，不打开终端问答。

被服务端拒绝，说明做法不对，换一种做法，不要原样重试：

| 错误 | 含义 | 怎么办 |
|------|------|--------|
| `ErrNotHolder` | 这个任务你已经不持有了（租约到期被别人接手，或被人收回） | 停止在这个任务上的工作，先把没提交的成果告诉用户 |
| `ErrCardVersionConflict` | 你读完之后，任务被别人改过 | 用 `get_card` 重新读，再决定怎么改 |
| `ErrProjectPathLocked` | 看板已经有项目路径 | 按第二节在看板记录问题，由人调整 |
| `ErrCardClaimed` | 别的 agent 正在做这个任务（领取或移动都不行） | 先做别的，等它交接或释放 |
| `ErrCardWaiting` | 它依赖的任务还没完成 | 先做别的 |
| `ErrEngineerBusy` | 指定的工程师在做别的任务 | 换一位空闲的，或者排队等 |
| `ErrNoIdleEngineer` | 同类型的工程师都在忙 | 这个任务排队，等有工程师交接再领 |
| `ErrEngineerBound` | 任务绑定了另一位研发工程师 | 改用任务绑定的那一位 |
| `ErrCardHumanOnly` | 这个任务只能由人处理 | 跳过 |
| `ErrServiceUnavailable` | 服务正在关闭或重启 | 过几秒再试 |

## 七、图片

人会在描述和评论里贴截图，地址形如 `![](/api/v1/attachments/<32 位编号>)`：用 `get_image` 把图读出来看，编号可以直接填整个地址。

自己要给任务配图（例如界面改动的截图）：先用 `upload_image` 上传，`path` 填本机图片文件的绝对路径（Slate 和你在同一台机器上才能用），拿不到文件时用 `data_base64`（整个请求不能超过 1 MiB，只适合很小的图片）；再把返回的 `markdown` 原样写进 `create_card`、`update_card` 的描述或 `comment_card` 的评论。只上传不引用，图片不会留在看板里。只收 PNG、JPEG、GIF、WebP，最大 5 MB。

## 八、合并已审查的本地分支

这一步由本机调度 agent 执行，审查子 agent 只负责验收。适用于按第四节创建的本地专属 Slate 分支，且审查列的下一列已标记为完成。以项目的列规则和授权为准。用登记的主工作区路径，目标是其中当前检出的分支，不按名字猜 `main` 或 `dev`。主工作区有未提交修改、目标未确定、分支不满足归属或权限不足时，评论说明具体卡点并保留现场，不改动主工作区来解锁。

升级不会覆盖已有看板的列指令。启用本地合并时，由看板管理人在「编辑列」调整审查通过后的流转，保留其他自定义指令。为专属 Slate 分支指定本节的「合并、记录并清理」流程，为其他任务保留原有的完成流转，并检查审查列下一列标为完成。

1. 创建任务分支时记录起点的完整 Git SHA。让审查子 agent 验证从起点到分支 HEAD 的整段提交，并向调度者回传实际验收的完整 SHA。卡片描述、研发交接和审查评论里的 Git 提交哈希只写前 6 位。存量任务的审查范围可从提交记录核实，范围不确定时请人在卡片上确认。

   审查通过后，读取本版本的 MCP 资源 `slate://scripts/slate-integrate.py`，原样保存到临时目录。运行 `python slate-integrate.py apply --help`，出现 `six-character approval ranges` 表示支持短审批凭证。旧版脚本仍可续办已保存的完整审批。若要新建审批而脚本还未支持短凭证，在评论中记录验收结论和脚本版本卡点，保留审查状态。

2. 用 `git rev-parse --disambiguate=<前 6 位>` 核对起点和已审 HEAD 各自只解析为对应完整 SHA。若有歧义或不匹配，在评论中说明并保留审查状态。用 `comment_card` 记录验收证据，单独附一行 `Slate review: <起点前6位>..<已验收 HEAD 前6位>`，以这条评论的 ID 作为合并凭证。

   续租并重新读取任务，确认仍由当前调度 agent 用测试工程师名额持有，仍处于原审查列，且未收到改变审批结论或分支的新信息。把最新 `get_card` 的结构化结果保存为临时 JSON 文件。用 Python 3.9+ 和 Git 运行，传入两端的完整 SHA。

   ```sh
   python slate-integrate.py --project "<主工作区>" --card-id <任务数字ID> --key <任务编号> --branch "<专属分支>" --approval <审批评论ID> --card-json "<任务JSON>" apply --base <起点SHA> --reviewed-head <已验收HEAD>
   ```

   脚本首次合并时核验审批的两个短哈希均唯一指向传入的完整提交。它在独立临时工作树依序 cherry-pick 审查过的提交，再快进主工作区。发布期间用 Git 的引用和索引锁核对目标分支、旧提交及审查提交，冲突时保留原有主工作区和任务工作树。Git 阻塞时先写明原因，保留审查结论、审查状态和分支。回执保存已核验的审批行和完整 SHA，重启时用同一卡片、同一审批和同一段提交重试，不重复 cherry-pick。若发布在更新文件或索引时中断，先检查主工作区、暂存区和目标引用。直接编辑文件或强制移除 Git 锁可以绕开 Git 的保护，遇到这类变更或进程中断遗留的锁，请保留现场并由人确认恢复方式。
3. 脚本成功后，再用 `get_card` 核实当前任务和审批仍有效。调用 `finish_card`，传最新 `version`、审查结论和脚本返回的 `merged_commits`。它会在一次操作内保存合并标记、附哈希前六位的评论，并移到完成列。人手动换列不会标为合并。若提交看板的结果不明，优先读回任务确认；尚未写入且同一审批仍有效时，用脚本原有结果续办。审批已撤回、任务已移列或版本冲突涉及验收内容时，停止流转并报告 Git 与看板状态。
4. 读回已完成并带有同一合并提交列表的任务，刷新临时 JSON 后以同组参数运行脚本的 `cleanup`（替换 `apply --base ... --reviewed-head ...`）。脚本验证主分支仍包含合并结果、任务工作树归属与分支 HEAD 未变，保持专属工作树对分支的检出占用直到删除该引用，再移除工作树。启动时可用 `python slate-integrate.py --project "<主工作区>" pending` 找回本仓库未清理的审批。仅在核对当前看板上的同一任务、审批和合并结果后继续，其他项目的记录跳过。清理会保留含未提交内容的工作树，包括 Git 忽略的本地文件。专属工作树已经缺失或分支被检出到其他工作树时，保留分支并报告。调度 agent 可让本任务执行者清理自己生成的临时产物，其余情况保留现场并在结果中说明。

   任务工作树的索引含 `assume-unchanged` 或 `skip-worktree` 时，清理会保留工作树、分支和索引。稀疏检出也可能设置 `skip-worktree`。由人检查这些文件及稀疏检出设置，再决定如何清理。
